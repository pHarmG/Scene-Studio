# Scene Studio as a Home Assistant add-on (weather-risk-bridge delivery model)

## Outcome

A fresh install of Scene Studio becomes: **HA web UI → Settings → Add-ons → App store → ⋮ → Repositories → paste `https://github.com/pHarmG/Scene-Studio` → Install → configure via the Configuration tab → Start**. No PowerShell, no SSH, no second machine, no hand-edited `apps.yaml`. Updates are handled by Supervisor's Update button. The repo is public, and the image is built on-device by Supervisor (weather-risk-bridge parity — `build.yaml` + Dockerfile, no registry).

Decisions locked with you: add-on route modeled on weather-risk-bridge · repo public (direct URL flow) · on-device image build · PowerShell workstation wizard **stays as-is** (advanced track) · add-on is **fresh installs only** (no migration of the existing AppDaemon-hosted install; it keeps using the workstation wizard + in-app updater).

## Architecture of the add-on

`addons/scene-studio/` in this repo (Supervisor scans subdirectories of an add-on repository for `config.yaml` — same single-repo pattern weather-risk-bridge uses). The add-on bundles its **own AppDaemon**, so the backend hosting model is unchanged: the adapter is still an AppDaemon app, AppDaemon HTTP still serves the Workbench at `/local/scene_studio/` and the API at `/api/appdaemon/scene_studio_api`.

**Filesystem split:** the immutable product payload lives in the image (`/opt/scene-studio/apps/scene_studio`, `/opt/scene-studio/www/scene_studio`); only rendered config, secrets, and the store live in the persistent `/data` (survives add-on updates untouched — Supervisor replaces the image, store preserved; no update-supervisor machinery needed on this track).

| File | Contents |
|---|---|
| `addons/scene-studio/config.yaml` | slug `scene_studio`, version pinned (gated == `VERSION`), arch amd64 + aarch64 (armv7 later), `startup: application`, `boot: auto`, `homeassistant: api`, host port 5050 (remappable in the Network tab; documented collision note with the community AppDaemon add-on), options + schema |
| `addons/scene-studio/build.yaml` | `build_from` HA base python images (amd64/aarch64, matching weather-risk-bridge's base-image style) |
| `addons/scene-studio/Dockerfile` | Multi-stage: `node:22` stage builds the Workbench (`npm ci` + `npm run build`, identity from `ARG BUILD_VERSION` → `SCENE_STUDIO_RELEASE_TAG=v$BUILD_VERSION`, `SCENE_STUDIO_BUILD_CHANNEL=addon`); HA-base-python stage `pip install appdaemon~=4.4 requests`, copies backend package + dist into `/opt/scene-studio`, writes backend `build-info.json` (channel `addon`, version from `BUILD_VERSION`), `HEALTHCHECK` curling the status endpoint, `CMD /run.sh` |
| `addons/scene-studio/run.sh` | Thin bashio entry: read options → invoke renderer → `exec appdaemon` with config dir `/data` and `app_dir` pointed at the image payload |
| `addons/scene-studio/render_config.py` | Pure-stdlib renderer (the testable core): reads `/data/options.json`, writes `/data/appdaemon.yaml` (hass plugin `ha_url: http://supervisor/core`, token via `${SUPERVISOR_TOKEN}` env interpolation; http on container :5050; `www` symlink → payload), `/data/apps.yaml` (managed block: `registry_admin` per mode option, `store_root: /data/scene_studio_store`, provider args), `/data/secrets.yaml` mode 0600 (Hue key stored under a NAME; apps.yaml references `!secret` — same wizard semantics: values never in apps.yaml) |

**Options (Configuration tab), mirroring the wizard's inputs:** `mode` (`setup` → registry_admin default | `normal` | `read_only` — replaces the manual apps.yaml flip after Workbench setup), `hue_host`, `hue_key` (password; optional), `hue_bridge_id`, `wled_host`, `hyperhdr_host`, `ignored_ha_entity_ids`. Hue LINK-button pairing is not possible from the add-on — docs state the prerequisite (existing Hue username from any Hue tool) or configure later.

**Supervisor app (`scene_studio_update`) is NOT provisioned** on this track; `SUPERVISOR_TOKEN` is natively available so the routine automation gateway works unchanged.

## Code changes outside `addons/`

- **Backend (small):** add-on delivery detection (`SCENE_STUDIO_ADDON=1` env, set in Dockerfile) surfaced in `/status.product.build` as `delivery: "addon"` with a tolerant build-info read (channel `addon` → identity is version-only, no 40-hex sha requirement); `/status.product.update` reports Supervisor-managed instead of offering in-app apply. **Workbench:** when `delivery: "addon"`, hide the in-app update apply flow and show "Updates are managed by Home Assistant (Settings → Add-ons)". No domain-core changes.
- **Release workflow** (`.github/workflows/release.yml`): new job on `ubuntu-latest` that `docker build`s the add-on (catches Node/pip breakage on-device builds would hit) and runs the add-on tests; existing gates and the three release assets are unchanged (the ZIP still serves the workstation track).
- **`scripts/version.py` / packaging:** no change to VERSION semantics; add-on `config.yaml` version joins the version gate (same rule as backend pyproject + workbench declarations).

## Tests

- `tests/installer/test_addon.py` (runs on windows-latest, offline): `config.yaml` version == `VERSION` and slug/name invariants; schema covers every option key; Dockerfile copies the expected trees; **renderer unit tests** — fresh boot → `registry_admin: true` + managed block shape, mode `normal`/`read_only` mapping, Hue key lands in secrets.yaml by name with `!secret` reference in apps.yaml, store root path, malformed options rejected; appdaemon.yaml token uses env interpolation (token value never rendered to disk).
- Backend: extend `/status` build-info tests for the `addon` channel; workbench smoke unchanged plus the delivery-conditional.
- Verification commands: `python -m pytest backend/tests -q`, `python -m pytest tests/installer -q`, workbench `npm run smoke && npm run build`, card suite, `python scripts/security/scan_secrets.py` before commit.

## Docs

- `docs/installation/START_HERE.md`: Route A (recommended) = App store install, written like weather-risk-bridge's README steps (add repo URL → Install → configure → Start → open Workbench URL); Route B = existing workstation wizard, marked advanced.
- New `docs/installation/ADDON_INSTALL.md`: options reference, mode flip after setup, Network-tab port remap + community-AppDaemon collision note, manual Lovelace card install (card auto-deploy is out of scope — the add-on doesn't map HA Core `/config`), Hue username prerequisite, updating via Supervisor.
- `AGENTS.md`: layout row for `addons/`, ownership note (add-on = fresh-install delivery track; workstation installer unchanged; in-app updater not provisioned in add-on mode). Root README quick-start section.

## Explicit non-goals

Migrating the existing AppDaemon-hosted install · card auto-deploy from the add-on · Ingress/sidebar embedding (host port first, like weather-risk-bridge) · armv7 · HACS-distributed card. Any live install onto `10.0.0.149` remains subject to the HA write policy — this plan's work is entirely offline and test-fake based.
